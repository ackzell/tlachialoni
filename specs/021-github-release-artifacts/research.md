# Research: GitHub Release Artifacts

**Date**: 2026-10-06

## R1: GitHub Actions Workflow Pattern

**Decision**: Use a single GitHub Actions workflow file (`.github/workflows/release.yml`)
that triggers on `v*` tag pushes, builds the app, and creates a GitHub Release.

**Rationale**: This is the standard pattern for CI/CD with GitHub Releases. The
maintainer already uses this exact pattern in the `tlapalli-vscode-theme` project,
so it is proven and familiar.

**Alternatives considered**:
- **Manual upload**: Build locally, then manually create a release and upload files.
  Rejected because it defeats the purpose of automation.
- **Third-party release actions**: Many exist but `softprops/action-gh-release` is
  the most widely used and already in the maintainer's toolkit.

## R2: Runner Selection

**Decision**: Use `macos-latest` runner.

**Rationale**: The app is macOS-only (arm64). electron-builder must run on macOS
to produce `.dmg` and `.zip` artifacts. The `macos-latest` runner provides the
necessary Xcode command-line tools and macOS SDK.

**Alternatives considered**:
- **Self-hosted runner**: Unnecessary overhead for a single-maintainer project.
- **Pinned macOS version**: Could pin to a specific version (e.g., `macos-14`) for
  reproducibility, but `macos-latest` is simpler and sufficient.

## R3: Version Verification

**Decision**: Extract version from the git tag and compare it to `package.json`.
Fail the workflow if they do not match.

**Rationale**: Prevents releasing artifacts with mismatched version metadata. This
is critical because the version is the single source of truth (spec 006) and
appears in artifact filenames, the app bundle, and the About panel.

**Alternatives considered**:
- **Skip verification**: Trust the tag. Rejected because a mismatched release is
  worse than no release.
- **Auto-correct package.json**: Modify the file to match the tag. Rejected because
  it violates the principle that version changes come only from tag commands.

## R4: Artifact Attachment

**Decision**: Attach both `.dmg` and `.zip` files to the GitHub Release.

**Rationale**: The `.dmg` is the primary installation method for macOS users. The
`.zip` provides an alternative for users who prefer to extract manually or need
the app for automated deployment.

**Alternatives considered**:
- **DMG only**: Simpler but excludes users who prefer zip.
- **ZIP only**: Smaller but not the standard macOS installation method.

## R5: Changelog Extraction

**Decision**: Extract the relevant version section from `CHANGELOG.md` and use it
as the release body.

**Rationale**: The changelog is already auto-generated by `commit-and-tag-version`.
Reusing it for the release body provides consistent, informative release notes
without additional tooling.

**Alternatives considered**:
- **Use commit messages directly**: Parse git log since last tag. Rejected because
  the changelog is already formatted and curated.
- **Manual release notes**: Write custom notes for each release. Rejected because
  it adds manual work and duplicates the changelog.

## R6: Signing and Notarization

**Decision**: No signing or notarization in the workflow. Artifacts are ad-hoc
signed, matching local build behavior.

**Rationale**: The maintainer cannot afford the Apple Developer license. Ad-hoc
signing is explicitly permitted by the constitution ("The default pipeline MAY
produce an ad-hoc/unsigned artifact for local use"). The workflow leaves room for
future Developer ID signing without restructuring.

**Alternatives considered**:
- **Developer ID signing**: Requires Apple Developer account ($99/year). Rejected
  due to cost.
- **Notarization**: Requires Apple Developer account. Rejected due to cost.
